Project Documentation

1. Project Overview

PedalPulse is a web-based database application developed to organize, manage, and explore historical Citi Bike trip information. The application was developed as part of a database systems project at Wayne State University.

Our project uses cleaned Citi Bike data from September 2026, containing 106,294 trip records and 222 bicycle stations. The data is stored in a PostgreSQL database consisting of two tables: trips and stations.

The application uses HTML and CSS for webpage design, JavaScript and AJAX for communication with the server, and PHP with PDO for connecting to the PostgreSQL database.

PedalPulse provides complete webpages for adding, deleting, and updating bicycle trip records. All three CRUD operations (Add Trip, Delete Trip, and Update Trip) use JavaScript fetch/AJAX POST requests communicating with PHP PDO scripts to modify records in the PostgreSQL database.

5. Setup Instructions

The following instructions describe how to set up and run PedalPulse locally with PostgreSQL and MAMP.

  1. Download the PedalPulse project files from the GitHub repository.
  2. Extract the downloaded ZIP folder.
  3. Install PostgreSQL 18 and pgAdmin 4.
  4. Create a PostgreSQL database named PedalPulse and restore the database from the provided backup.
  5. Verify that the database contains the trips and stations tables.
  6. Install MAMP and start the Apache server.
  7. Place the PedalPulse project files inside the MAMP htdocs directory.
  8. Configure the PHP database connection using the correct PostgreSQL host, port, database name, and username.
  9. Store the PostgreSQL password securely outside the public website directory.
  10. Open the local PedalPulse website through the MAMP server.

Local Website Address: http://localhost:8888/PedalPulse/

The local application uses PHP with PDO to communicate with PostgreSQL. The Apache server and PostgreSQL server must be running for database operations.

GitHub Pages hosts the static frontend files but does not execute PHP. Database functionality must therefore be tested using a PHP-enabled server.

6. User Guide

Home: View the project introduction, dataset information, and database overview.

Add Trip: Open the Add Trip page and enter the required bicycle trip information. Submitting the form sends an AJAX POST request to add_trip.php, which inserts the new record into the PostgreSQL trips table via PDO and displays a confirmation message.

Delete Trip: Open the Delete Trip page and enter the unique Ride ID of the record to be removed.

After clicking the Delete Trip button, the application asks the user to confirm the deletion.

Once confirmed, JavaScript sends an AJAX POST request to the PHP backend. PHP uses a prepared SQL statement to delete the matching record from the PostgreSQL trips table.

The webpage displays a success message if the trip is deleted or an error message if the Ride ID cannot be found.

Update Trip: Open the Update Trip page and enter an existing Ride ID along with the fields to modify. Submitting sends an AJAX POST request to update.php, which updates the specified columns in PostgreSQL via PDO.

Documentation: Review the project overview, development team, software requirements, setup instructions, database structure, and dataset information.

Current Development Status: Add Trip, Delete Trip, and Update Trip operations are fully implemented with JavaScript AJAX and PHP PDO backends connected to the local PostgreSQL database.

8. Database Structure

PedalPulse uses a relational PostgreSQL database named PedalPulse. The database contains two main tables: stations and trips.

Stations Table

The stations table stores information about Citi Bike stations. Each station is identified by a unique station ID.

  • station_id - Unique station identifier and primary key
  • station_name - Name of the bicycle station
  • latitude - Geographic latitude
  • longitude - Geographic longitude

Trips Table

The trips table stores individual Citi Bike ride records. Each trip is identified by a unique Ride ID.

  • ride_id - Unique trip identifier and primary key
  • rideable_type - Type of bicycle used
  • started_at - Trip starting date and time
  • ended_at - Trip ending date and time
  • duration_minutes - Total trip duration
  • start_station_id - Starting station identifier
  • end_station_id - Ending station identifier
  • member_casual - Rider membership category

The start_station_id and end_station_id fields reference station identifiers in the stations table. This structure helps organize trip information and station details in separate relational tables.

9. Backend Implementation and Testing

PedalPulse uses JavaScript, AJAX, PHP, and PostgreSQL to process database operations.

For the Delete Trip operation, JavaScript collects the Ride ID entered by the user and sends it to delete_trip.php using an asynchronous POST request.

The PHP backend connects to PostgreSQL through PDO and executes a prepared DELETE statement using the supplied Ride ID.

The backend returns a JSON response, which JavaScript displays on the Delete Trip webpage.

Testing Results: The PostgreSQL database connection was successfully tested using PHP. The initial database contained 106,294 trip records.

A temporary test trip with the Ride ID PEDALPULSE_DELETE_TEST_001 was inserted into the trips table.

The record was deleted through the Delete Trip webpage. The application displayed the message "Trip deleted successfully!"

A follow-up SQL SELECT query in pgAdmin 4 returned zero rows for the test Ride ID, confirming that the record had been removed from the PostgreSQL database.

This test verified communication between the HTML form, JavaScript, PHP backend, and PostgreSQL database.
